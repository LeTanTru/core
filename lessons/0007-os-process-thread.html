OS Foundations: Process vs Thread, Context Switching & Concurrency

Hiểu sự khác biệt Process vs Thread và tại sao JavaScript chọn single-threaded event loop.

⏱ ~20 phút · 🎯 Mục tiêu: Giải thích được Process isolation, Thread race condition, và lý do JS dùng single-thread thay vì multi-thread.

🌉 Bắc cầu từ cái bạn đã biết

Process như căn nhà riêng — mỗi nhà có cổng khóa, bộ nhớ riêng, không ai vào nhà người khác được. Thread như người trong một căn nhà — cùng chia sẻ phòng bếp, phòng khách (bộ nhớ). Khi bạn mở Chrome với 5 tab → Chrome spawn 5 process riêng biệt (Site Isolation): tab lỗi không crash tab khác.

1. Process — Ngôi nhà với ổ khóa riêng

Một process là instance đang chạy của một chương trình. OS cấp cho mỗi process:

  • Virtual address space riêng (stack + heap + code + data segment)
  • File descriptor table riêng (mở file, socket)
  • Trạng thái CPU riêng (registers, program counter)
💡 Vì sao isolation quan trọng?

Fault isolation: process A crash → chỉ A chết, process B không bị ảnh hưởng. Chrome dùng điều này: mỗi tab là một Renderer Process riêng. Nếu tab YouTube crash vì WebGL lỗi, Gmail vẫn sống.
Security isolation: process A không thể đọc bộ nhớ của process B → ngăn tấn công Spectre/Meltdown cross-process.

Trade-off: Spawn process nặng — cần sao chép toàn bộ address space (fork), tốn ~1–5ms, RAM riêng. Giao tiếp giữa process (IPC) phải qua pipe, socket, shared memory — phức tạp và chậm hơn thread.

Inter-Process Communication (IPC)

Vì process không chia sẻ bộ nhớ, chúng cần IPC để nói chuyện:

Cơ chế IPC Đặc điểm Ví dụ trong browser
Pipe / Named Pipe Một chiều, FIFO stdout → stdin giữa process cha/con
Unix Domain Socket Hai chiều, nhanh Renderer ↔ Browser process
Shared Memory Cực nhanh, nhưng cần mutex GPU Process chia sẻ frame buffer
Message Passing An toàn nhất (copy data) postMessage() giữa window/iframe

2. Thread — Người trong cùng một căn nhà

Một thread là đơn vị thực thi nhỏ hơn process. Các thread trong cùng process chia sẻ address space (heap, global variables, file descriptors) nhưng mỗi thread có stack riêng.

Process Thread
Bộ nhớ Riêng hoàn toàn Chia sẻ heap, globals
Stack Riêng Riêng (mỗi thread)
Spawn cost Cao (~MB RAM, ms) Thấp (~KB, µs)
Giao tiếp IPC (chậm, phức tạp) Shared memory (nhanh, nguy hiểm)
Crash isolation ✅ An toàn ❌ 1 thread crash → cả process chết

Race Condition — Cạnh tranh điều kiện

Vì thread chia sẻ bộ nhớ, khi 2 thread đọc-sửa-ghi cùng một biến không có đồng bộ hóa, kết quả không xác định:

Pseudo-code · Race condition với shared counter 
// Biến chia sẻ — cả 2 thread cùng đọc/ghi
let counter = 0;

// Thread A và Thread B chạy đồng thời (parallel)
// Cả hai đều thực hiện: counter = counter + 1

// Thực tế CPU thực hiện 3 bước:
// 1. READ: đọc counter (= 0) vào register
// 2. ADD:  cộng 1 → register = 1
// 3. WRITE: ghi register (1) trở lại counter

// Nếu Thread A và B đều READ trước khi WRITE:
// A đọc 0, B đọc 0, A ghi 1, B ghi 1 → counter = 1 (sai! Phải là 2)

Mutex / Lock — Chìa khóa chỉ có một bản

Giải pháp: dùng mutex (mutual exclusion) — chỉ 1 thread được vào "vùng nguy hiểm" (critical section) tại một thời điểm. Thread khác phải đợi (block). Trade-off: giải quyết race condition nhưng tạo ra bottleneck + nguy cơ deadlock (2 thread chờ nhau mãi mãi).

3. Context Switching — Chi phí ẩn

CPU chỉ có N core. Để chạy M thread (M > N), OS phải liên tục context switch: lưu trạng thái thread đang chạy (registers, program counter, stack pointer) → nạp trạng thái thread tiếp theo.

⚠️ Context switch không miễn phí

Mỗi context switch tốn 1–10µs (save/restore registers + flush TLB + cache miss do địa chỉ bộ nhớ thay đổi). Với hàng ngàn thread, CPU dành phần lớn thời gian cho context switching thay vì công việc thực tế — gọi là thrashing.

Đây là lý do Node.js server dùng event loop (1 thread) thay vì multi-thread (1 thread/request như PHP truyền thống) có thể handle hàng chục nghìn concurrent connections mà không bị thrash.

4. Concurrency vs Parallelism — Hai khái niệm khác nhau

Concurrency (Đồng thời) Parallelism (Song song)
Định nghĩa Xử lý nhiều việc bằng cách xen kẽ (interleaving) Thực sự chạy đồng thời trên nhiều core
Yêu cầu 1 CPU core là đủ Cần >1 CPU core
Ví dụ Event loop của Node.js Worker threads, GPU shader
Phép ẩn dụ Bếp trưởng xoay xở 5 chảo một mình 5 đầu bếp mỗi người một chảo

JavaScript là concurrent (event loop xử lý nhiều callback xen kẽ) nhưng không parallel (chỉ 1 thread JS chính). Web Workers cho phép parallel nhưng không chia sẻ state.

5. Tại sao JavaScript chọn single-threaded?

💡 Lý do lịch sử + thiết kế

1995 — Brendan Eich thiết kế JavaScript cho Netscape Navigator. Mục tiêu: ngôn ngữ đơn giản để web designer (không phải lập trình viên) dùng được. Multi-threading phức tạp, dễ gây deadlock/race condition → chọn single-thread.

Lợi thế của single-thread:

  • ✅ Không cần mutex/lock cho DOM manipulation → DOM API đơn giản hơn nhiều
  • ✅ Không có race condition trong code JS thông thường
  • ✅ Event loop xử lý I/O bất đồng bộ cực kỳ hiệu quả (non-blocking I/O)
  • ✅ Code dễ debug, dễ reason về thứ tự thực thi

Nhược điểm:

  • ❌ CPU-intensive task (hash, image processing, ML inference) sẽ block main thread → UI freeze
  • ❌ Không tận dụng được CPU multi-core trực tiếp trong code JS thông thường

6. Web Workers — Parallel trong Browser

Web Workers (HTML Living Standard) cho phép chạy JS trong thread riêng biệt, không có quyền truy cập DOM. Giao tiếp qua postMessage() — truyền bản sao dữ liệu (structured clone), không chia sẻ reference.

JavaScript · Web Worker — offload CPU-intensive task 
// === main.js (chạy trên main thread) ===

// Tạo Worker — chạy trong OS thread riêng biệt
const worker = new Worker('worker.js');

// Gửi dữ liệu sang Worker (structured clone — COPY, không share reference)
worker.postMessage({ task: 'sum', data: [1, 2, 3 /* ... 1 triệu phần tử */] });

// Nhận kết quả — main thread KHÔNG bị block trong lúc đợi
worker.addEventListener('message', (e) => {
  console.log('Kết quả:', e.data.result);
  worker.terminate(); // dọn dẹp Worker khi xong
});

// UI vẫn mượt — event loop main thread tiếp tục chạy

// === worker.js (chạy trên Worker thread) ===
self.addEventListener('message', ({ data: { task, data } }) => {
  if (task === 'sum') {
    // Tính toán nặng — không ảnh hưởng main thread
    const result = data.reduce((acc, n) => acc + n, 0);
    self.postMessage({ result }); // trả kết quả về main
  }
});

7. Code Demo Vitest: Mô phỏng Race Condition

Vitest · race-condition.test.js
import { test, expect } from 'vitest';

// Mô phỏng "yield" giống context switch giữa 2 task bất đồng bộ
const yield_ = () => new Promise(r => setTimeout(r, 0));

// Task KHÔNG an toàn: yield giữa READ và WRITE → race condition
async function unsafeIncrement(state, times) {
  for (let i = 0; i < times; i++) {
    const val = state.counter; // READ — đọc giá trị hiện tại
    await yield_();            // "context switch" — task khác chen vào đây!
    state.counter = val + 1;   // WRITE — ghi lại giá trị cũ + 1
  }
}

test('race condition: 2 task +3 mỗi task → kỳ vọng 6 nhưng ra ít hơn', async () => {
  const state = { counter: 0 };

  // Chạy 2 task "đồng thời" — xen kẽ nhau tại mỗi await
  await Promise.all([
    unsafeIncrement(state, 3), // Task A muốn +3
    unsafeIncrement(state, 3), // Task B muốn +3
  ]);

  // Kết quả thực tế thường là 3, không phải 6!
  // Vì mỗi lần A và B cùng đọc val=cùng giá trị, một increment bị mất
  console.log('Counter với race:', state.counter); // thường in ra 3
  expect(state.counter).toBeLessThan(6); // ✅ race condition xảy ra
});

// Task AN TOÀN: không yield giữa READ-WRITE → không race condition
async function safeIncrement(state, times) {
  for (let i = 0; i < times; i++) {
    state.counter++; // atomic trong JS: read-add-write không bị ngắt
  }
}

test('safe: tuần tự, không yield → luôn đúng', async () => {
  const state = { counter: 0 };
  await safeIncrement(state, 3); // hoàn tất +3 trước
  await safeIncrement(state, 3); // rồi mới +3 tiếp
  expect(state.counter).toBe(6); // ✅ luôn chính xác
});
🎯 Bộ câu hỏi thực tế ôn tập & Phỏng vấn thực chiến
  1. Câu hỏi 1: JavaScript là single-threaded. Vậy làm sao Node.js / Browser xử lý được hàng nghìn tác vụ đồng thời mà không bị treo?
    Trả lời 60s: JS Engine chỉ chạy single-thread cho phần tính toán đồng bộ trên Call Stack, nhưng các tác vụ I/O (network fetch, disk read, timers) được ủy thác sang Web APIs (trên Browser) hoặc libuv thread pool (trên Node.js) chạy ngầm ở background OS threads. Khi I/O hoàn tất, callback được đẩy vào Queue để Event Loop lấy lên Call Stack khi stack rỗng. Đây là mô hình Concurrency (xen kẽ) qua Non-blocking I/O.
  2. Câu hỏi 2: Tại sao Google Chrome lại chấp nhận tốn nhiều RAM để chạy Multi-Process (Site Isolation) thay vì dùng Multi-Threading gọn nhẹ hơn?
    Trả lời 60s: Chrome ưu tiên 2 yếu tố sống còn: Fault Isolation (tab này crash hoặc dính lỗi WebGL/vòng lặp vô hạn thì các tab khác vẫn hoạt động bình thường, không làm sập cả trình duyệt) và Security Isolation (ngăn chặn tấn công rò rỉ bộ nhớ cross-site như lỗ hổng phần cứng Spectre/Meltdown vì 2 domain khác nhau không thể đọc chung vùng nhớ Process của nhau). Đánh đổi RAM lấy sự ổn định và bảo mật.
  3. Câu hỏi 3 (Tình huống Frontend thực tế): Trong React/Vue, Race Condition khi gọi API tìm kiếm (Autocomplete/Search) xảy ra như thế nào và cách xử lý triệt để?
    Trả lời 60s: Khi người dùng gõ nhanh từ "re" sang "react", 2 request API được gửi đi. Nếu request "re" gặp độ trễ mạng và phản hồi chậm hơn request "react", kết quả của "re" sẽ về sau cùng và ghi đè lên UI, hiển thị sai dữ liệu. Khắc phục: Sử dụng AbortController để hủy request cũ trước khi phát request mới, hoặc dùng biến requestId / active flag trong cleanup effect để bỏ qua response đã hết hạn.
  4. Câu hỏi 4: Web Worker giao tiếp với Main Thread qua cơ chế nào và tại sao nó không được phép thao tác trực tiếp với DOM?
    Trả lời 60s: Web Worker giao tiếp qua postMessage() sử dụng thuật toán Structured Clone (sao chép dữ liệu, không chia sẻ vùng nhớ con trỏ). Web Worker bị cấm truy cập DOM vì nếu nhiều thread cùng lúc sửa đổi cây DOM sẽ dẫn tới Race Conditions và Deadlock trên layout tree, phá vỡ kiến trúc single-thread đơn giản và an toàn của web.
