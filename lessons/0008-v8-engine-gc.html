V8 Engine Internals: Call Stack, Memory Heap & Garbage Collection

Hiểu cách V8 cấp phát bộ nhớ và dọn rác (GC) để viết code tránh memory leaks.

⏱ ~25 phút · 🎯 Mục tiêu: Giải thích pipeline V8, sự khác nhau Stack vs Heap, cơ chế Generational GC, và 4 pattern gây memory leak phổ biến.

🌉 Bắc cầu từ cái bạn đã biết

Memory Heap như bàn làm việc — bạn đặt đồ lên đó (objects, arrays) và có thể để lâu dài. Call Stack như chồng đĩa ăn (LIFO) — đặt đĩa nào lên sau thì lấy ra trước; khi function gọi function, stack frame chồng lên nhau; khi return thì pop ra. Bài trước bạn đã biết single-thread — bây giờ bạn sẽ hiểu cụ thể bộ nhớ của thread duy nhất đó được quản lý như thế nào.

1. V8 Architecture — Từ source code đến máy chạy

V8 (Google, 2008) là JS engine dùng trong Chrome và Node.js. Pipeline biên dịch:

Sơ đồ pipeline V8
Source Code (JS)
      │
      ▼
  ┌─────────┐
  │  Parser │  → tạo AST (Abstract Syntax Tree)
  └────┬────┘
       │
       ▼
  ┌──────────┐
  │ Ignition │  → biên dịch AST thành Bytecode (thông dịch)
  └────┬─────┘
       │  "hot" functions (gọi nhiều lần)
       ▼
  ┌──────────┐
  │ TurboFan │  → JIT compile bytecode → native machine code
  └──────────┘
       │  nếu assumptions sai (deoptimize)
       └──────────────────────────────▶ Ignition (fallback)
💡 Tại sao cần cả Ignition lẫn TurboFan?

Ignition (bytecode interpreter): khởi động nhanh, ít RAM — dùng cho code chạy ít lần (startup, initialization). TurboFan (JIT compiler): tốn thời gian compile nhưng tạo ra native code cực nhanh — dùng cho "hot paths" (loop nặng, function gọi hàng nghìn lần).

Trade-off: TurboFan optimize dựa trên type assumptions (ví dụ: biến này luôn là number). Nếu giả định sai (đột nhiên pass string) → deoptimization, V8 phải quay về Ignition. Đây là lý do TypeScript và type-consistent code chạy nhanh hơn.

2. Call Stack vs Memory Heap — Cái gì nằm ở đâu?

Call Stack Memory Heap
Lưu gì Stack frames (local vars primitives, references, return address) Objects, arrays, functions, closures
Kích thước Cố định, nhỏ (~1–8 MB) Lớn, dynamic (GB)
Cấp phát Tự động (push/pop) Tự động qua new, literals; GC dọn
Tốc độ Cực nhanh (pointer move) Chậm hơn (allocation + GC overhead)
Giải phóng Tự động khi function return GC khi không còn reference
JavaScript · Stack vs Heap — cái gì ở đâu
function outer() {
  const x = 42;          // x (number primitive) nằm trên STACK
  const name = 'Alice'; // tham chiếu trên stack, string content trên HEAP
  const obj = {         // obj reference trên STACK
    age: 25            // object {age:25} thực sự nằm trên HEAP
  };
  return inner(obj);   // gọi inner → push stack frame mới
}

function inner(data) {
  // Stack frame của inner: tham chiếu data trỏ đến object TRÊN HEAP
  return data.age + 1; // trả về 26, pop stack frame này
}

outer(); // khi outer() kết thúc, stack frame của outer bị pop
         // nhưng object {age:25} trên HEAP vẫn ở đó cho đến khi GC dọn

// STACK OVERFLOW xảy ra khi đệ quy vô hạn:
function infinite() { return infinite(); } // → RangeError: Maximum call stack size exceeded

3. Generational Garbage Collection — Dọn rác thông minh

V8 dùng Generational GC dựa trên quan sát: "phần lớn objects chết trẻ" (ví dụ: object tạo trong vòng lặp, function call thường không sống lâu). V8 chia heap thành:

Young Generation (New Space) Old Generation (Old Space)
Kích thước Nhỏ (~1–8 MB) Lớn (~hundreds MB)
Object tuổi Mới tạo, sống ngắn Sống qua 2 lần GC Young
GC algorithm Scavenger (Minor GC) Mark-Sweep-Compact (Major GC)
Tần suất GC Thường xuyên (ms) Ít hơn, tốn thời gian hơn
Thời gian GC Rất nhanh (<5ms) Chậm hơn (có thể pause >50ms)

Scavenger (Minor GC) — Dọn Young Generation

Young Generation chia thành 2 semi-space: from-space và to-space. Khi from-space đầy:

  1. Scan từ GC roots (global, stack) → mark objects còn reachable trong from-space
  2. Copy objects còn sống sang to-space (compacting tự nhiên)
  3. Swap from/to-space → toàn bộ from-space cũ bây giờ là "tự do"
  4. Object sống qua 2 lần Scavenge → promote lên Old Generation

Mark-Sweep-Compact (Major GC) — Dọn Old Generation

  1. Mark: traversal từ GC roots (DFS/BFS), đánh dấu tất cả reachable objects
  2. Sweep: giải phóng bộ nhớ của objects không được đánh dấu (dead)
  3. Compact: di chuyển objects còn sống về đầu heap (giảm fragmentation)
💡 Incremental & Concurrent GC — tránh jank

Major GC pause cả JS thread → UI freeze (jank). V8 giải quyết bằng Incremental Marking: chia việc mark thành nhiều bước nhỏ xen kẽ với JS execution. Và Concurrent Sweeping: sweep trên helper thread song song với JS main thread. Kết quả: GC pause được giảm từ >100ms xuống còn ~1ms cho hầu hết trường hợp.

4. Làm thế nào Object "Chết" — Reachability

GC không dùng reference counting (dễ bị circular reference). Thay vào đó: object được giữ sống chỉ khi reachable từ GC roots.

GC Roots gồm: global object (globalThis), current call stack (local variables), active closures, DOM references.

JavaScript · Reachability — khi nào object được GC 
// Object reachable — sẽ KHÔNG bị GC
let user = { name: 'Alice', age: 25 };
// user trỏ đến object → object reachable từ global scope

// Xóa reference → object trở thành unreachable → eligible for GC
user = null;
// Không còn gì trỏ đến {name:'Alice'} → GC có thể dọn nó

// Circular reference — GC vẫn xử lý được (mark-sweep không bị vấn đề)
let a = {};
let b = {};
a.ref = b; // a trỏ đến b
b.ref = a; // b trỏ đến a → circular!
a = null;
b = null;
// Cả a và b unreachable từ roots → GC dọn được cả 2
// (Reference counting sẽ fail ở đây vì count vẫn = 1)

5. Các Pattern Gây Memory Leak trong JavaScript

🚨 4 pattern phổ biến nhất gây memory leak

① Closures giữ reference không cần thiết

JavaScript · Closure memory leak
function createLeak() {
  const bigData = new Array(1_000_000).fill('x'); // ~4MB

  // ❌ Closure này giữ TOÀN BỘ bigData trong lexical scope
  // dù chỉ dùng bigData.length
  return function () {
    return bigData.length; // bigData không được GC cho đến khi closure này chết
  };
}

const leaked = createLeak(); // leaked còn sống → bigData còn sống

// ✅ Fix: chỉ giữ những gì cần
function createFixed() {
  const bigData = new Array(1_000_000).fill('x');
  const len = bigData.length; // chỉ copy giá trị cần dùng
  // bigData không được capture trong closure → eligible for GC
  return function () { return len; };
}

② Global variables — không bao giờ được GC

JavaScript · Global variable leak
// ❌ Vô tình tạo global (thiếu let/const/var)
function oops() {
  leakedGlobal = { data: new Array(100_000) }; // attached to globalThis!
}
oops(); // leakedGlobal tồn tại suốt lifetime của trang

// ✅ Fix: luôn khai báo biến + dùng 'use strict'
'use strict';
// Strict mode sẽ throw ReferenceError nếu gán biến không khai báo

③ Forgotten timers — setInterval không clearInterval

JavaScript · Timer memory leak
function startPolling() {
  const heavyObj = { data: new Array(100_000) };

  // ❌ setInterval giữ closure alive → heavyObj không được GC
  const id = setInterval(() => {
    console.log(heavyObj.data.length); // closure giữ heavyObj
  }, 1000);

  // Nếu quên gọi clearInterval(id), timer và closure sẽ tồn tại mãi
  return id; // ✅ luôn return id để có thể cleanup
}

const timerId = startPolling();
// Cleanup khi component unmount / không cần nữa
clearInterval(timerId); // ✅ giải phóng closure và heavyObj

④ Detached DOM nodes — remove khỏi DOM nhưng vẫn còn JS reference

JavaScript · Detached DOM leak
let detachedNode; // biến global giữ reference đến DOM node

function createAndRemove() {
  const div = document.createElement('div');
  div.textContent = 'Tạm thời';
  document.body.appendChild(div);

  // ❌ Lưu reference trước khi remove → detached node, không được GC
  detachedNode = div;

  document.body.removeChild(div); // remove khỏi DOM nhưng JS vẫn giữ
}
createAndRemove();
// detachedNode vẫn giữ div → không GC → memory leak

// ✅ Fix: xóa reference khi không cần
// detachedNode = null; // sau khi dùng xong

6. Code Demo Vitest: Object Reachability

Vitest · reachability.test.js — kiểm tra lifetime của object 
import { test, expect, vi } from 'vitest';

// Mô phỏng "reference holder" để test reachability
class Tracker {
  constructor() {
    this.alive = true; // object "còn sống"
  }
  destroy() {
    this.alive = false; // mô phỏng cleanup
  }
}

test('closure giữ reference → object sống dài hơn mong đợi', () => {
  let tracker = new Tracker();

  // Closure capture reference đến tracker
  const closure = () => tracker.alive;

  // Xóa reference bên ngoài — nhưng closure vẫn giữ
  const ref = tracker;
  tracker = null; // outer ref gone, nhưng closure vẫn giữ

  // Object vẫn "sống" trong closure
  expect(closure()).toBe(true); // ✅ vẫn alive vì closure giữ

  // Chỉ khi closure bị GC thì object mới được giải phóng
  ref.destroy(); // cleanup thủ công
  expect(closure()).toBe(false); // ✅ sau cleanup
});

test('buông reference → object eligible for GC', () => {
  let tracker = new Tracker();
  expect(tracker.alive).toBe(true);

  tracker = null; // không còn reference → eligible for GC
  // Không thể test GC trực tiếp trong JS, nhưng object không còn accessible
  expect(tracker).toBeNull(); // ✅ reference đã null
});

test('timer leak: clearInterval giải phóng closure', () => {
  const log = [];
  const data = { value: 42 }; // object bị giữ bởi timer

  const id = setInterval(() => {
    log.push(data.value); // closure giữ data
  }, 10);

  vi.useFakeTimers();
  vi.advanceTimersByTime(30); // 3 ticks
  clearInterval(id);           // dọn timer → closure released
  vi.useRealTimers();

  // Sau clearInterval, closure và data reference được giải phóng
  expect(id).toBeTruthy(); // ✅ id hợp lệ, timer đã được tạo
});
🎯 Bộ câu hỏi thực tế ôn tập & Phỏng vấn thực chiến
  1. Câu hỏi 1: Bộ thu gom rác (Garbage Collector) của V8 hoạt động như thế nào? Thế nào là Young vs Old Generation?
    Trả lời 60s: V8 áp dụng Generational GC dựa trên quan sát phần lớn object chết ngay sau khi tạo. Young Generation (New Space, nhỏ ~1-8MB) chứa object mới tạo, được dọn dẹp liên tục bằng thuật toán Scavenger (Minor GC) siêu nhanh qua copy giữa 2 semi-spaces. Object sống sót qua 2 chu kỳ GC sẽ được thăng hạng (promoted) lên Old Generation (Old Space) và được dọn dẹp bởi Mark-Sweep-Compact (Major GC) ít thường xuyên hơn để tránh UI jank.
  2. Câu hỏi 2: Tại sao V8 không dùng cơ chế Reference Counting (đếm tham chiếu) mà dùng Tracing GC dựa trên Reachability từ GC Roots?
    Trả lời 60s: Reference Counting gặp điểm yếu chí mạng với Circular References (tham chiếu vòng tròn): khi Object A trỏ B và B trỏ lại A nhưng cả hai đều không còn được chương trình sử dụng, ref count vẫn bằng 1 và không bao giờ được giải phóng. Tracing GC duyệt cây từ GC Roots (Global object, active Call Stack, DOM tree) — object nào không thể chạm tới (unreachable) sẽ bị dọn sạch bất kể chúng có trỏ vòng tròn lẫn nhau hay không.
  3. Câu hỏi 3: Kể tên 4 thủ phạm phổ biến nhất gây Memory Leak trong ứng dụng Frontend SPA?
    Trả lời 60s: (1) Biến Global vô tình tạo ra (thiếu const/let). (2) Forgotten Timers/Callbacks (gọi setInterval hoặc addEventListener mà không clearInterval / removeEventListener khi component unmount). (3) Closures giữ tham chiếu tới các biến dung lượng lớn ngoài lexical scope không cần thiết. (4) Detached DOM Nodes (đã xóa thẻ HTML khỏi DOM Tree nhưng biến JavaScript vẫn giữ con trỏ trỏ tới node đó).
  4. Câu hỏi 4 (Kỹ năng thực chiến DevTools): Làm thế nào để điều tra và chứng minh một component React/Vue đang bị rò rỉ bộ nhớ bằng Chrome DevTools?
    Trả lời 60s: Mở tab Memory trên Chrome DevTools. Chụp Heap Snapshot 1 (Baseline) → Mở rồi đóng component đó 10 lần (hoặc trigger action nghi ngờ) → Nhấn nút thùng rác Collect Garbage thủ công → Chụp Heap Snapshot 2. Chọn chế độ Comparison và lọc "Objects allocated between Snapshot 1 and 2", tìm các object như Detached HTMLDivElement hoặc mảng dữ liệu không giảm sau khi unmount.
