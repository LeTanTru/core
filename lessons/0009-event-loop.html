Event Loop Sâu: Call Stack, Microtasks, Macrotasks & rAF

Hiểu chính xác thứ tự thực thi của Promise, setTimeout, requestAnimationFrame trong Event Loop.

⏱ ~25 phút · 🎯 Mục tiêu: Predict đúng output của bất kỳ đoạn code async nào; giải thích cơ chế Event Loop khi phỏng vấn.

🌉 Bắc cầu từ cái bạn đã biết

Bài trước bạn đã hiểu V8 Call Stack (LIFO) và JavaScript single-thread. Bây giờ câu hỏi là: nếu chỉ có 1 thread, làm sao JS xử lý nhiều việc? Event Loop như nhân viên bưu điện cần mẫn: xử lý từng công việc một (đảm bảo không race), nhưng ưu tiên thư nhanh (microtasks) trước khi lấy thư thường (macrotasks) mới từ hộp thư.

1. Call Stack — LIFO, Stack Overflow

Call Stack là nơi V8 theo dõi function nào đang chạy. Mỗi function call tạo một stack frame (lưu local variables + return address). Function return → frame bị pop.

JavaScript · Call Stack minh họa
function a() {
  b(); // gọi b → push frame b lên stack
}
function b() {
  c(); // gọi c → push frame c lên stack
}
function c() {
  console.log('inside c'); // Stack: [a, b, c] — c trên đỉnh
  // return → pop c, trở về b
}
a(); // Stack: [a] → [a,b] → [a,b,c] → [a,b] → [a] → []

// Stack Overflow — đệ quy vô hạn
function infinite() {
  return infinite(); // push mãi → hết stack space
}
// → Uncaught RangeError: Maximum call stack size exceeded
💡 Tại sao Call Stack phải rỗng trước khi Event Loop chạy callback?

JavaScript là single-thread. Event Loop chỉ có thể đẩy callback vào execution khi Call Stack hoàn toàn rỗng. Nếu stack đang bận (code JS đang chạy), callback phải đợi trong queue. Điều này giải thích vì sao setTimeout(fn, 0) không chạy "ngay lập tức" — nó phải đợi stack rỗng.

2. Web APIs & Macrotask Queue

Web APIs (setTimeout, setInterval, fetch, DOM events) không thuộc V8 — chúng do browser (hoặc Node.js libuv) cung cấp. Khi callback của chúng sẵn sàng, chúng được đẩy vào Macrotask Queue (còn gọi là Task Queue / Callback Queue).

Nguồn Loại Queue
setTimeout / setInterval Timer Macrotask
DOM events (click, input…) UI event Macrotask
XHR / fetch callback I/O Macrotask
MessageChannel.postMessage Messaging Macrotask
setImmediate (Node.js) Timer Check phase (giữa macrotasks)

3. Microtask Queue — Ưu tiên cao hơn Macrotask

Microtask Queue được xử lý sau mỗi macrotask và trước khi Event Loop lấy macrotask tiếp theo. Toàn bộ Microtask Queue phải rỗng mới chuyển sang macrotask tiếp theo.

Nguồn Microtask Ghi chú
Promise.then() / .catch() / .finally() Phổ biến nhất
queueMicrotask(fn) Thêm microtask thủ công (WHATWG spec)
MutationObserver Theo dõi DOM changes
async/await (bên dưới là Promise) await tạo microtask

4. Event Loop Algorithm — Vòng lặp chính xác

Pseudo-code · Event Loop algorithm
// Event Loop — chạy liên tục (simplified)
while (true) {
  // BƯỚC 1: Lấy MỘT macrotask từ Macrotask Queue (nếu có)
  const task = macrotaskQueue.dequeue();
  if (task) {
    execute(task); // chạy task → Call Stack
  }

  // BƯỚC 2: Drain TOÀN BỘ Microtask Queue (quan trọng!)
  while (microtaskQueue.length > 0) {
    const microtask = microtaskQueue.dequeue();
    execute(microtask); // microtask có thể thêm microtask mới → vẫn drain hết
  }

  // BƯỚC 3: Render (nếu cần — browser only)
  if (renderNeeded && timeToRender) {
    runAnimationFrameCallbacks(); // requestAnimationFrame callbacks
    render();                       // Layout → Paint → Composite
  }

  // Lặp lại — lấy macrotask tiếp theo
}
🚨 Microtask starvation — vòng lặp vô hạn trong microtask

Nếu microtask liên tục thêm microtask mới, Macrotask Queue và render KHÔNG BAO GIỜ được thực thi — UI freeze hoàn toàn. Ví dụ: function loop() { Promise.resolve().then(loop); } loop(); → tab treo ngay lập tức.

5. requestAnimationFrame (rAF) — Trước Render, Sau Microtasks

requestAnimationFrame(fn) — callback fn được gọi ngay trước browser render frame (~60fps = mỗi 16.7ms). rAF KHÔNG phải macrotask cũng không phải microtask — nó là bước riêng biệt trong vòng lặp browser.

💡 Dùng rAF đúng chỗ

✅ Dùng rAF cho animation, DOM update cần synchronized với frame rate.
❌ Không dùng setTimeout(fn, 16) thay rAF — timer không đảm bảo đúng frame boundary, có thể tearing.

Trong Node.js không có rAF (không có browser rendering). Thay vào đó Node.js có process.nextTick() — thực ra chạy trước cả Microtask Queue (đặc thù của Node.js, không có trong browser).

7. Code Demo Vitest: Predict Output

JavaScript · Thứ tự execution — thử predict trước khi xem đáp án 
console.log('1'); // synchronous → chạy ngay

setTimeout(() => {
  console.log('2'); // macrotask → chạy SAU tất cả microtasks
}, 0);

Promise.resolve().then(() => {
  console.log('3'); // microtask → chạy TRƯỚC macrotask
  queueMicrotask(() => {
    console.log('4'); // microtask từ trong microtask → drain tiếp theo
  });
});

queueMicrotask(() => {
  console.log('5'); // microtask → chạy trước setTimeout
});

console.log('6'); // synchronous → chạy ngay sau '1'

// OUTPUT: 1 → 6 → 3 → 5 → 4 → 2
// Giải thích:
// Sync: 1, 6 (call stack)
// Microtasks: 3 (Promise.then) → thêm '4' vào queue → 5 (queueMicrotask) → 4
// Macrotask: 2 (setTimeout)
Vitest · event-loop-order.test.js — kiểm tra thứ tự execution 
import { test, expect, vi } from 'vitest';

test('microtask (Promise) chạy TRƯỚC macrotask (setTimeout)', async () => {
  const log = [];

  setTimeout(() => log.push('macrotask'), 0); // vào Macrotask Queue

  Promise.resolve().then(() => {
    log.push('microtask'); // vào Microtask Queue
  });

  // Đợi cả macrotask và microtask complete
  await new Promise(r => setTimeout(r, 10));

  // Microtask phải chạy trước macrotask
  expect(log).toEqual(['microtask', 'macrotask']); // ✅
});

test('queueMicrotask từ trong microtask được drain ngay trong cùng vòng', async () => {
  const log = [];

  Promise.resolve().then(() => {
    log.push('micro-1');
    queueMicrotask(() => log.push('micro-2')); // thêm vào queue trong khi drain
  });

  setTimeout(() => log.push('macro'), 0);

  await new Promise(r => setTimeout(r, 10));

  // micro-2 được drain TRƯỚC macro, dù được thêm sau micro-1
  expect(log).toEqual(['micro-1', 'micro-2', 'macro']); // ✅
});

test('async/await desugars thành Promise microtask', async () => {
  const log = [];

  async function asyncTask() {
    log.push('before await'); // sync — chạy ngay
    await Promise.resolve();  // yield — tạo microtask cho phần sau
    log.push('after await');  // tiếp tục sau khi microtask queue drain
  }

  asyncTask();              // bắt đầu task (không await ở đây)
  log.push('sync after call'); // sync — chạy trước 'after await'

  await new Promise(r => setTimeout(r, 10));

  expect(log).toEqual([
    'before await',  // sync trong asyncTask
    'sync after call', // sync ngoài asyncTask
    'after await',   // microtask resume
  ]); // ✅
});
🎯 Bộ câu hỏi thực tế ôn tập & Phỏng vấn thực chiến
  1. Câu hỏi 1 (Đọc Code Phản Xạ): Đoạn code sau in ra màn hình thứ tự nào? Giải thích chi tiết luồng Event Loop: 
    console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => {
  console.log('3');
  queueMicrotask(() => console.log('4'));
});
queueMicrotask(() => console.log('5'));
console.log('6');
    Trả lời 60s: Thứ tự: 1 → 6 → 3 → 5 → 4 → 2. Giải thích: 1 và 6 chạy đồng bộ trên Call Stack trước. Khi Stack rỗng, Event Loop drain toàn bộ Microtask Queue: chạy 3 (Promise), lúc này đẩy 4 vào cuối hàng đợi microtask, tiếp tục chạy 5 (queueMicrotask trước đó), rồi drain tiếp 4. Chỉ sau khi sạch bóng microtasks, Event Loop mới lấy macrotask 2 (setTimeout) từ Task Queue.
  2. Câu hỏi 2: requestAnimationFrame (rAF) nằm ở vị trí nào trong chu kỳ Event Loop? Tại sao làm animation mượt 60fps phải dùng rAF thay vì setTimeout(fn, 16)?
    Trả lời 60s: rAF nằm ở bước Rendering Phase của trình duyệt (chạy sau khi Microtasks drain hết và ngay trước khi trình duyệt thực hiện Layout & Paint). setTimeout(fn, 16) không đồng bộ với tần số quét màn hình (Display Refresh Rate) và có thể bị trễ do các macrotask khác chắn đường, gây ra hiện tượng rớt frame (Jank/Tearing). rAF đảm bảo callback chỉ chạy chính xác 1 lần trước mỗi lần màn hình chuẩn bị quét lại điểm ảnh.
  3. Câu hỏi 3: Hiện tượng Microtask Starvation (đói Macrotask) là gì? Đoạn code nào có thể gây treo UI mà không ném lỗi Stack Overflow?
    Trả lời 60s: Microtask Starvation xảy ra khi một microtask liên tục thêm microtask mới vào hàng đợi (ví dụ: function loop() { Promise.resolve().then(loop); } loop();). Vì Event Loop bắt buộc phải drain cạn kiệt toàn bộ Microtask Queue trước khi render hoặc lấy Macrotask tiếp theo, trình duyệt sẽ bị đóng băng hoàn toàn (UI Freeze), không nhận tương tác click hay timer mà không báo lỗi Maximum Call Stack Size Exceeded (vì Call Stack đã pop sau mỗi microtask).
  4. Câu hỏi 4: queueMicrotask(fn) khác gì với Promise.resolve().then(fn)? Khi nào nên dùng queueMicrotask?
    Trả lời 60s: Cả hai đều đưa callback vào Microtask Queue, nhưng queueMicrotask() là Web API chuẩn (WHATWG) không tạo ra đối tượng Promise trung gian trên Memory Heap → nhẹ hơn, nhanh hơn và không cần xử lý unhandled promise rejections. Dùng queueMicrotask khi bạn muốn hoãn thực thi một hàm đồng bộ xuống ngay sau tick hiện tại mà không cần đến tính năng Promise chaining.
